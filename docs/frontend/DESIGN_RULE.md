# DESIGN_RULE — フロントエンドデザイン規約（AI エージェント向けハーネス）

UI を新規作成・大幅変更するとき**必ず**この規約に従う。目的はひとつ: **「AI が作ったとわかるサイト」を出荷しないこと。**

## 0. 機構的ガードレール（プロンプト以前の絶対制約）

1. 色・フォント・角丸・余白は **`packages/ui/src/theme.css` のセマンティックトークン経由のみ**。
   - 禁止: Tailwind デフォルトパレット（`bg-blue-500` 等）/ 任意値（`p-[13px]`, `text-[#8b5cf6]`）/ inline style の色指定。
2. 新しい色・フォントが必要 = **トークンを追加・変更してから使う**（theme.css を編集し、理由をコメントに残す）。
3. 共有コンポーネント（`@app/ui`）があるものを再実装しない。無いレイアウトはアプリ側で素の Tailwind で組む。

## 1. 設計プロセス（2 パス強制）

コードを書く前に、**トークン計画を先に文章で出す**。計画なしで JSX を書き始めない。

**新規画面・見た目の大幅変更では、パス 1 を 2〜3 案作り、`.agents/skills/design-select`（`design-select` スキル）で HTML モックとしてブラウザに提示し、人間に選ばせてから実装する。**（軽微な変更はパス 1 のテキスト提示のみで可。）

**パス 1 — 計画（コード禁止）:**
1. 題材を 1 文で: 「誰が・何のために・このページで何をするか」。ビジュアルの語彙は題材の世界から引く（例: 帳簿、路線図、フィルムラベル、値札、索引カード…）。
2. トークン計画: 名前付き 4–6 色（hex 明記）/ 2 役割以上の書体（個性のある display + 静かな body、データは mono）/ 余白・角丸の方針。
3. レイアウト概念を 1 文 + 必要なら ASCII ワイヤ。
4. **シグネチャ要素を 1 つ**決める: このページが記憶される 1 点（例: 台帳のヘアライン、巨大な数字、非対称な余白）。大胆さはこの 1 点に集中投資し、他は静かに保つ。

**パス 2 — 自己批評 → 実装:**
- 計画を見て自問: **「この計画は、同種のどんな依頼にも出てくる generic 案ではないか？」** Yes なら計画からやり直す。
- 実装ではすべての色・書体・余白の判断を計画から導出する。計画にない装飾を追加しない。

## 2. NEVER / INSTEAD（既知の「AI 顔」収束点）

| NEVER（AI の指紋） | INSTEAD（代わりにやること） |
|---|---|
| Inter / Roboto / Open Sans / Lato / 素の system-ui を主書体に | 下の書体メニューから題材に合う組を選ぶ（高コントラストなペアリング: serif×geometric sans、display×mono） |
| 「逃げ先」の定番: Space Grotesk + Instrument Serif イタリック 1 語アクセント | 同上。**メニューの中でも毎回同じ組を選ばない** |
| 紫→青グラデーション、多色グラデ背景、大きな色付き glow | 支配色 1 + 鋭いアクセント 1。背景に表情が要るなら紙目・罫線・微グラデ 1 枚まで |
| クリーム地 #F4F1EA + セリフ見出し + テラコッタ / 近黒地 + アシッドグリーン / 新聞風ヘアライン紙面 — の **3 大 AI デフォルト面相** | 題材由来のパレットを自作する（IDE テーマ・文化的な美術様式・実在の紙物から引く） |
| centered hero + pill バッジ + 3 枚均等 feature カード | 非対称レイアウト、1 カラムの文書構造、表・台帳・タイムラインなど内容の形に沿う構造 |
| カード上辺/左辺の 3–4px 色ストリップ（最も確実な AI 指紋） | 枠は 1px の line トークン、強調は背景・タイポグラフィで |
| 内容が手順でないのに 01/02/03 ナンバリング | 内容の実態に合う構造（表・定義リスト・散文） |
| 絵文字箇条書き・ALL-CAPS eyebrow ラベル | sentence case の本文で説明する |
| 全要素同じ border-radius・7 種のカードスタイル混在 | radius はトークン 1 つ、カードは 1 プリミティブを強く |
| 散発的な micro-interaction 山盛り | モーションは **1 箇所のオーケストレーション**（例: 初回ロードの stagger）だけ。追加のアニメ自体が AI 指紋 |

**書体メニュー**（fontsource で自己ホスト。ここから選ぶか、題材に合う他候補を提案して人間に確認）:
display: Fraunces / Bricolage Grotesque / Newsreader / Libre Caslon / Zodiak 系 serif、幾何系なら Archivo / Anybody。body: Public Sans / IBM Plex Sans / Source Sans 3。mono/データ: JetBrains Mono / IBM Plex Mono / ui-monospace スタック。

## 3. 品質フロア（宣言せずに常に満たす）

- レスポンシブ（モバイル 375px〜）。`min-h-dvh`。
- キーボード操作可能・`focus-visible` リング可視（トークン色）。
- テキストコントラスト WCAG AA（muted 系トークンも AA を保つ）。
- `prefers-reduced-motion` を尊重（アニメを入れた場合）。
- フォームは `<label htmlFor>` 必須（`@app/ui` の `Field` を使う）。

## 4. コピー（文言）規約

- 能動態・sentence case。売り文句でなく事実を書く。
- ボタンはユーザーの操作対象で命名（「Submit」でなく「Save changes / Add entry」）。ボタンと完了トーストで動詞を揃える。
- エラーは「何が起きたか + どう回復するか」（例: "Saving failed. Your entry is still in the form — try again."）。謝罪だけのエラーを書かない。

## 5. 手本

`services/example_service/src/web/App.tsx` はこの規約を通した実装例（題材: 台帳/ledger、シグネチャ: 二重罫のマストヘッド + ヘアライン台帳、display 書体は 2 箇所のみ）。新しい画面を作るときの参照点にする。ただし**コピーするのは規約の適用方法であって、見た目そのものではない**（全サービスが台帳になるのは NEVER 表の「収束」そのもの）。

## 6. モックアップ駆動ワークフロー(`/design-select` の後)

実プロダクト移植で確立した運用。`/design-select` で選ばれた HTML モックは `docs/frontend/mockups/<name>/` に保存し（最初の 1 件で作られる。台帳は [`mockups/README.md`](./mockups/README.md)）、以後こう扱う:

- **モック = 見た目の正、theme.css = 意味の正**の二層分離。モックの生値(hex・px)は**インライン CSS のままコピペしない** — theme.css のセマンティックトークンへ翻訳してから React 実装する(ルール 5)。
- モックは静的 1 状態しか描いていない。**ローディング / 空 / エラー / レスポンシブ(375px〜)は品質フロア(§3)で補完**する(モックに無いから作らない、は誤り)。
- **却下されたデザイン方向は「禁止」として明文化**して mockups/README に台帳化する(過去に人間が否定した見た目へ戻さないため)。
- モックが無い画面は、**既存モックの語彙(トークン・部品)で新規作成**する。`/design-select` の再実施は見た目の方向を変えるときだけ。
