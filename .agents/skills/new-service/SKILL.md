---
name: new-service
description: Scaffold a new service (one Worker serving SPA + API, with contracts + D1) from the example_service template.
---

Scaffold the service name supplied by the user, following `specs/README.md` and `AGENTS.md`. If no name was supplied, ask for it. Confirm the plan before large changes (absolute rule #10: no unapproved arch/library decisions).

1. **Specify first**: copy `specs/_service-template` to `specs/<service-name>`, fill in `00_service-spec.md` (boundary, entity, API surface, owned D1).
2. **Contract**: add `packages/contracts/src/<service-name>.ts` (Zod schemas) and export from `index.ts`.
3. **Service**: copy `services/example_service` to `services/<service-name>` (minus `dist`, `node_modules`, `.wrangler`, `worker-configuration.d.ts`, `migrations/*`). Rename: package to `@app/<service-name>`, D1 `database_name` to the service name (underscores OK), wrangler `name` to the **hyphenated** form (Worker names are DNS labels — e.g. dir `example_service` → name `example-service`), dev/e2e ports to unused ones. Copy `.dev.vars.example` too and run `make dev-vars`. Replace the `item` entity (worker routes, Drizzle schema, web UI) with the new domain's. **Write tests first** (`services/example_service/test` as a model). The copied template also contains an optional `src-tauri` shell: either remove its scripts/dependencies and files when native is out of scope, or replace its product name, identifier, fixed `TAURI_*_API_ORIGIN` build variable, platform overlays, dev port, and native auth storage keys before using it. Keep the regular Vite server `strictPort: true`; if mobile HMR is needed, support `TAURI_DEV_HOST` without broadening the Rust release-origin allowlist. A production domain receives `JWT_PUBLIC_KEY` only; admin retains `JWT_PRIVATE_KEY`. Keep `AUTH_DEV_PRIVATE_KEY` / `AUTH_DEV_GRANT` local-only.
4. **DB**: `pnpm --filter @app/<service-name> db:generate` then `db:migrate:local`; add a `cloudflare_d1_database` + output in `infra/terraform/cloudflare`.
5. **UI**: follow `docs/frontend/DESIGN_RULE.md` — produce the pass-1 token plan in text before writing JSX. Do NOT copy the ledger look from example_service; apply the process, not the visual.
6. **Wire the platform services**: add the new D1 to `services/ops` monitoring (one row in `opsTargets()` + `MYNAME_DB_ID` var + Bindings) so it gets backups + capacity + health checks. If admin should sync orgs to this service instead of the scaffold, swap admin's `EXAMPLE_SERVICE` binding target.
7. **Deploy boundary and verify**: add a `make deploy/<service-name>` target and exact guarded `deploy` / `db:migrate:remote` package scripts. Worker deploy/migration are protected-main CI-only; the local entry points must fail closed and pass the production-config preflight. Add `@app/<service-name>` to the ordered production deploy chain and e2e jobs in `.github/workflows/ci.yml` (example_service itself is never deployed — your service takes its place). Also add the service's D1 id, service binding, health/backup target, and caller-specific secret names; the repository boundary checker rejects any one omitted. Register only `JWT_PUBLIC_KEY` and the caller-specific internal key for each binding direction on the domain Worker; name the admin-to-domain key `ADMIN_TO_<DOMAIN>_KEY`, generate a distinct value for every domain, and never copy admin's private key or reuse an internal key across directions. Use `scripts/put-production-secret.mjs` with one complete local bundle so duplicate direction keys are rejected. When the first Worker must be created, add/update the reviewed `production-bootstrap.yml` input and allowlist mapping; bootstrap is only a protected-main `workflow_dispatch` with production-environment approval, never a local `--bootstrap` call. Then run `pnpm install`, `pnpm check` (must be green), `pnpm --filter @app/<service-name> e2e`, and if native is kept, the corresponding `make build/<service-name>/tauri` / Rust checks.
